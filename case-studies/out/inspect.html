The problem

Email spoofing and missing security headers are two of the most common, most overlooked domain misconfigurations. Existing checkers either bury the result in jargon (raw SPF/DKIM/DMARC record dumps) or grade a site without explaining what the grade actually means for a non-specialist.

The approach

A small Express backend performs the DNS lookups for SPF, DKIM, and DMARC, and fetches security headers for the target site, then grades the headers A through F similar to Mozilla Observatory. Each result includes a plain English explanation of what it means and why it matters, added directly in response to the question "does 58 percent mean this site is not secure enough", since a percentage alone does not answer that.

Architecture decisions

A small Express backend was necessary here, unlike the fully client side tools in this portfolio, because DNS lookups (SPF, DKIM, DMARC) and header fetches against an arbitrary third party domain are blocked by browser CORS policy and would leak the visitor doing the lookup. That backend dependency is exactly why it was the one tool that went silently down: it is the tradeoff of needing a server at all, and the fix was adding it to the site wide uptime checker that now polls every 5 minutes and drives the status dot on every project card.

Lesson learned

A backend service that looks fine can still die quietly. The systemd unit here has Restart=on-failure, but the process was stopped by a clean SIGTERM rather than a crash, so it did not auto-restart and sat dead for about 22 hours before a routine check caught it. A grading tool is only useful if it is actually up, this is a reminder to add real uptime monitoring, not just a restart policy.
